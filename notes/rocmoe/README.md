# rocmoe — MoE Super-Kernel v3 (Layout-P + receiver-pull + MonolithEP hot loop)

> **目标**: 在 8x MI355X 上做 MoE 层的 fused super-kernel + comm-compute overlap, 用 RocMoE-bak 的架构 (Layout-P / receiver-pull / scoreboard) + MonolithEP 的 GEMM hot loop (`mfma_tile.h` 99.3% MFMA), 把 BF16 wall 从 monolith-moe 4.82 ms (512 t/g) 推到训练真实工况 (T_src=2048+) 也反超 PyTorch+RCCL
> **平台**: 8x MI355X (gfx950, CDNA4, XGMI 全互联)
> **栈**: ROCm 7.2 / hipcc / PyTorch 2.12+rocm7.1 / Primus
> **目标模型**: DeepSeek-V3 671B (256E EP8 -> 32 local, top_k=8, H=7168, F=2048)
> **工作仓库**: `~/workspace/RocMoE/` (clean, 全新)
> **参考仓库**:
>   - `~/workspace/MonolithEP/` — 性能最高 (super 34.07 ms / iter, GEMM 99.3% MFMA, push 路径)
>   - `~/workspace/RocMoE-bak/` — 架构最干净 (super 2.21 ms vs iso 4.26 ms = 1.93x, Layout-P / pull 路径)

## 与 monolith-moe 的关系

monolith-moe 仍是 **生产线** —— 4.82 ms / 8x MI355X, Primus + DSV3 e2e 已通, loss parity 已验; RocMoE-v2 是 **下一代研究线**, 用作:

1. **roofline 对照** —— 必须打过 monolith-moe (BF16 同工况) 才算架构成功;
2. **GEMM 资产共享池** —— `mfma_tile.h` 是双向移植的源头, 任何调优先在 monolith-moe / MonolithEP PASS, 再 cherry-pick;
3. **Layout-P 验证地** —— 如果 RocMoE-v2 跑赢, 后续把 Layout-P 反向移植回 monolith-moe 也成立。
