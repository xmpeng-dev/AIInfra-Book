1. 问题背景

算力增速几十年远快于内存带宽(memory wall)。MoE 稀疏激活虽降 FLOPs,却降低计算密度并放大内存压力——序列越长、batch 越大,越受内存子系统而非 FLOPs 约束。过往用 token dropping/padding 限缓冲区伤精度;较新系统聚焦稀疏计算复杂度,但 dispatch 辅助缓冲 + 中间结果物化仍占内存大头。

内存瓶颈复杂度DeepSeek 量级实例
① Token routing bufferO(L·K·d)L≈2M, K=4, d=6144, bf16 → ≈94 GB/层
② FFN 中间激活(SiLU/SwiGLU)前向 O(L·h),反向更高L≈2M, h=24576, bf16 → ≈98 GB/FFN 层

2. 核心方法:元数据路由 + kernel co-design

机制一:元数据驱动 dispatch(不物化 routed token)

dispatch 阶段只建 4 个轻量索引,expert 计算时从原始未重排激活张量 on-the-fly gather,输出时按逆映射 on-the-fly reduce 直接写回 (L,d);反向用同一反向映射 scatter,避免把 (L,d) 梯度扩展成 (L·K,d)。

索引结构形状作用
expert_token_indicesL×k按专家拼接的 token-id 列表
expert_token_offsetsE+1每专家 token 数的 exclusive prefix sum
token_expert_indicesL×k逆映射,按 token 序存 expert-id
token_index_mapL×k每 token 的 k 个专家输出在中间缓冲的位置
 
atomic-free 3 步 dispatch 构建(替代多趟 radix sort):
  Step1  dense_token_map (L×E 位图)  每 warp 一批 token 行,专家 id 唯一→无 warp 内冲突
  Step2  列归约数每专家 token 数 → expert_lengths → prefix sum → expert_offsets
  Step3  两阶段 location map(shared 内 tile 级 exclusive scan + 加全局 offsets)
         → 并行写入 expert_token_indices,全程无 atomic

机制二:SwiGLU 融合 kernel + 激活检查点

观察:SiLU/SwiGLU 计算轻(点乘 + tall-skinny L≫d)但中间物化重,是 memory-bandwidth-bound。融合:一次 load x,同时流过 W1,W2 两个 GEMM,寄存器/shared 内算 SiLU(a) 并立即乘 b,只把最终输出写回 global——省 a,b 的写回+重读,x 读取减半。反向重算 SiLU(廉价点乘换内存),两分支梯度 tiled 就地聚合,消除临时 global 缓冲。

3. 主要实验(单 H100,单 MoE 层,fwd+bwd,vs Megablocks)

场景指标MoEBlaze vs Megablocks
SiLU峰值激活内存最高 3.6×(conf4:6100 vs 22000 MB)
SiLU端到端加速1.4–3.7×
SwiGLU峰值激活内存~4×(conf3:~10000 vs >40000 MB)
SwiGLU端到端加速2–6.2×(比 SiLU 更高更稳)

收益随 L(序列)与 k(激活专家数)成比例放大;conf1(k=1、小 L)最小,大 d/大 E 最大。SwiGLU > SiLU:复杂激活物化更多,融合+重算省的带宽更关键。软件 PyTorch 2.0.1 + CUDA 12.1;激活内存用 saved-tensor hooks 统计。

4. 与 monolith-moe / rocmoe 的对照(重点)

MoEBlaze 是我们 super-kernel 在「单卡计算/内存 kernel」维度上的强互证——它不做 comm overlap(正是我们的差异化留白),但每一招我们都在 IPC/kernel 层踩过对应坑。

MoEBlaze我们(monolith-moe / rocmoe)关系
元数据索引、不物化 routed token、on-the-fly gatherLayout-P + receiver-pull + pack_perm同源:拒绝物化中间大缓冲
atomic-free 3 步 dispatch 构建sender pack 用 counting-sort + atomicAdd(非确定序)⭐ 值得对标:换 atomic-free 或可省争用 + 解耦 backward
SwiGLU 融合:一次 load、寄存器算 SiLU、只写最终输出Phase 2.1 SwiGLU pre-compute → FC2 全 DTOLDS结论一致:SwiGLU 中间量不落 HBM,已落地
backward 重算 SiLUdecomposed backward(复用 forward 保存量)可评估:bwd SiLU 也走重算
融合 batched-GEMM 吃 wgmma / TMAmfma_tile.h(99.3% MFMA)+ DirectToLDSwgmma→MFMA、TMA→DTOLDS,招式可平移

三条最有用的结论

  • atomic-free dispatch 构建是我们没试过的方向。 当前 atomicAdd pack 的非确定序逼得 backward 必须复用 sender 的 pack_perm;改成 dense-map + 两阶段 prefix-sum 的确定性构建,可能既省 atomic 争用又解耦 backward,列为 rocmoe 候选实验。
  • SwiGLU 融合 + backward 重算被独立验证有效——forward 侧 pre-compute 已上,backward 侧 SiLU 重算是低风险增量。
  • 定位再确认: MoEBlaze 4–6× 是单卡、无通信的内存/kernel 收益;我们的战场是 XGMI in-kernel comm-compute overlap,两者正交、可叠加。

5. 局限与复现

  • 仅单卡、单 MoE 层;多机分布式列为 future work。
  • baseline 只对 Megablocks;无收敛/精度曲线佐证「不掉精度」。
  • 负载不均、numerical stability、long-context 极端场景未系统评测。
  • 代码未开源;硬件依赖 H100(wgmma/TMA),非 Hopper 收益可能下降。
