COMET:面向 MoE 的细粒度计算-通信 Overlap

MLSys 2025 ByteDance Seed 上海交大 8×H800 万卡部署

论文: arXiv:2502.19811 (v3) · PDF · 代码 (Flux/COMET)
英文题名: Comet: Fine-grained Computation-communication Overlapping for Mixture-of-Experts
笔记路径: slab/papers/comet.md
TL;DR MoE 层的跨 GPU 通信平均占整模型 47% 时间;既有方案用粗粒度 chunk 流水线 overlap,既伤 GEMM 利用率又对不齐。 COMET 在单个融合 kernel 内做 tile 级 overlap,靠两招:① shared-tensor 依赖分解(沿独立维度切 + 按 source rank 重排 tile,本地 token 先算);② 自适应 thread-block 分配(comm 块与 GEMM 块物理隔离占不同 SM,生产/消费块数 np/nc 按 shape 离线 profile 后运行时选)。 8×H800:隐藏 86.5% 通信,单 MoE 层 1.96×、端到端 1.71×,已在万卡集群部署省数百万 GPU 小时。
重读修正(2026-06-02): 旧版笔记把方法误写为「warp 专用化 + RDMA + 反向 overlap + 内存省 35%」并拿 FlowMoE(2510.00207,晚于本文 8 个月)对照、给出「2.3×」等数字,均非原文。COMET 实为 thread-block(线程块)专用化、用 NVSHMEM(非裸 RDMA)、只优化前向、内存仅 2MN(可忽略),真实加速 1.96× 单层 / 1.71× 端到端。本页据 arXiv v3 全文重写。

1. 问题背景

MoE 把专家分散到多 GPU,每层都要 dispatch(All-to-All)→ FC1/FC2 GroupGEMM → combine(All-to-All)。 在 8×H800 + Megatron-LM 上,MoE 层的设备间通信平均占整模型 47% 执行时间——通信是头号瓶颈。

既有 overlap(FasterMoE / Tutel / PipeMoE / ScheMoE)都走粗粒度 chunk 流水线,有两个根本低效:

低效机理
粗粒度切分伤计算效率chunk 越小,每 expert token 越少,GroupGEMM tile 利用率掉,t1+t2 > t;首尾 comm 段无法被覆盖 → GPU 空转
kernel 级调度不可控comm/comp 封成独立 kernel 放不同 stream,资源分配非确定、comp 与 recv 错位;MoE 动态路由让每 expert 的 M 运行时才知道

两个洞察:① 解决 token(通信单位)与 128×128 tile(计算单位)的粒度失配 是高效 overlap 的关键;② 资源比例要在 kernel 内运行时自适应(随 shape / TP / 硬件而变)。

2. 核心设计:两条流水线 + 两个机制

一个 MoE 层 = 两条生产者-消费者流水线,由一块 shared tensor(全局形状 (M×topk, N))连接:

layer0  comm→comp :  dispatch(All-to-All) ──► FC1 GroupGEMM
layer1  comp→comm :  FC2 GroupGEMM ──► top-k reduce + combine(All-to-All)

机制一:Shared-tensor 依赖分解

  • ① 分解(decompose)——只沿消费者「数据独立」的维度切:layer0 的消费者是 GEMM,token 间独立 → 切 M(token)维;layer1 的消费者含 top-k reduce(沿 M 归约)→ 只能切 N 维。
  • ② 重排(reschedule)——重组回 tile 粒度,优先调度消费者能立刻用上的部分:
    • layer0:token 按 source rank 排序,GroupGEMM 从本地 token 的 tile 先算,远端 token 同时还在传 → 计算覆盖通信。
    • layer1:GroupGEMM 按列(N)执行,前 TN 列一算完,reduce+combine 立即起,不必等所有 expert 算完。
layer0 重排:按 source rank 排序,本地 token 的 tile 先算
                                    GroupGEMM 计算序列 ──→
  原始 shared tensor      重排后        tile#0    tile#1    tile#2
  (token 乱序混排)   ─►  本地(rank0) ─►  [本地]    [远端]    [远端]
                        远端(rank1)       ↑         ↑
                                      立即可算   此时还在 NVLink 传输
                        → 本地 tile 的计算 覆盖 远端 token 的通信

layer1 重排:GroupGEMM 按列(N)执行,而非逐 expert 顺序
        N ──►                          前 TN 列一算完
  ┌──┬──┬──┬──┐  Expert#0             reduce+combine 立刻起步
  │①│②│③│④│   执行顺序 ① → ② → ③ → ④  (不必等所有 expert)
  ├──┼──┼──┼──┤  Expert#1
  │  │  │  │  │  top-3 reduce 沿 M 维(列内)归约
  └──┴──┴──┴──┘
   TN

这步纯属数据布局 + 计算顺序重排,不改 GEMM kernel 本身。

机制二:自适应 workload 分配

  • Thread-block 专用化(水平融合):反对把 comm I/O 塞进 GEMM 的 prologue/epilogue(垂直融合,会拖垮 Hopper TMA 异步流水);改为让 comm 块与 comp 块物理隔离、占不同 SM。GEMM 块沿用与融合前完全相同的 CUTLASS 实现(producer warp 走 TMA 搬数,consumer warp 发 tensor-core MMA),计算效率不被通信干扰;comm 块从 global memory 读结果、做 reduce、经 NVSHMEM 收发。可移植到 Ampere/Volta,只换 compute 块即可。
  • 自适应块数划分:n = np(生产者) + nc(消费者/通信),最优划分点随 shape/并行策略漂(TP=8 时 M 4096→16384 使最优 nc 18→26;TP 8→4 使 nc 26→46)。COMET 预编译多档划分点 kernel + 离线 profile 存 metadata + 运行时按 metadata 选。

实现:约 12k 行 C++/CUDA + 2k 行 Python,集成 Megatron-LM;GEMM 用 CUTLASS(行索引缓存进寄存器省 K 迭代访存);通信用 NVSHMEM;buffer 仅 2MN(32–64 MB,可忽略)。

4. 与 RocMoE-v2 super-kernel 的对照(重点)

COMET 与正在做的 RocMoE-v2(8×MI355X 上的 MoE 融合 super-kernel)是同一类工作的两个独立实现。把两者拉到同一张表,RocMoE 踩过的坑与 COMET 的设计高度互证。

三个最强的「同源」点

  • 物理隔离 comm 与 comp 是收敛结论。 COMET 明确反对把 comm 塞进 GEMM 块(「comm warp 干扰同块 comp warp + 吃不满带宽」)。RocMoE 在 M2-G α 撞到一模一样的现象:dispatch CU 与 GEMM stub WG 用 launch_bounds(_,2) 共驻一 CU 时 dispatch wall 5.51→8.43 ms(+53%)(共抢 wave scheduler / L2);随后 M4-α 用 __launch_bounds__(_,1) 强制分到不同 CU,dispatch wall 全段 −35~37%。 这就是 COMET「thread-block 专用化」在 CDNA4 上的等价物——两边独立得出「通信和计算必须占不同物理执行单元」。 
   COMET (Hopper SM)                RocMoE-v2 (CDNA4 CU)
   ─────────────────                ────────────────────
   comp SM  │  comm SM              GEMM CU  │  dispatch CU
   (CUTLASS)│ (NVSHMEM)             (mfma_tile)│ (IPC pull)
            │                                │
   thread-block 专用化               __launch_bounds__(_,1)
   (np/nc 自适应)                    (kSubWGs: 184G + 64D)
            ▲                                ▲
            └─ 同一收敛结论:comm/comp 占不同物理执行单元 ─┘
            反例代价:塞一起 → COMET TMA 卡顿 / RocMoE dispatch +53%
  • 重排让消费者从本地/已就绪数据先算。 COMET 按 source rank 排序、本地 tile 先算;RocMoE 用 receiver-pull + per-block scoreboard。都把「等全部 token」降成「等这个 tile/block 的 token」。
  • comm/comp 资源比例 shape-dependent。 COMET 的 nc 随 M/TP 漂(18→46,离线 profile);RocMoE 的 kSubWGs 五档 sweep + 三次返工才钉在 8。都承认这个划分点不能拍死。

RocMoE 可借鉴 COMET 的点

  • 预编译多档划分点 + 运行时按 (T, skew) 选 kernel:RocMoE 的 kSubWGs 是 build-time 单值,hot_cov50 下 dispatch 会变 critical path,值得做成可选。
  • layer1 按列(N)产出即推 combine:RocMoE 可评估 FC2 是否也能列产出即推,进一步藏 combine。
  • 行索引缓存进寄存器:对照 mfma_tile.h 取行索引路径,看是否有同类省访存。

RocMoE 更激进 / 更难处

  • COMET 一次只融合半层、靠 NVSHMEM 兜底;RocMoE 把整个前向五 phase 融成一个 persistent kernel 且无 NVSHMEM,手写 IPC + cross-rank barrier,grid_sync 调度税成了主要开销(Phase 1 grid_sync_v2 单项 −14%)——这是 COMET 不会遇到的。
  • COMET 在带宽充裕的 NVLink 上 1.96×;RocMoE 在 XGMI 上要先反超 PyTorch+RCCL,且 receiver-pull 比 push 每 token 慢 ~43%(架构性),靠 overlap 藏掉。

5. 局限与复现

  • 只优化前向,反向 overlap 未涉及。
  • 依赖 NVSHMEM(NVIDIA 专有),非 NVIDIA 平台需等价细粒度 GPU-initiated 通信原语。
  • 自适应划分靠离线 profile + 预编译多 kernel,新 shape/硬件需重 profile。
  • 评测限 8 GPU 单节点;代码已开源 bytedance/flux(CUDA 12.3 + NVSHMEM 2.11 + CUTLASS + Megatron-LM)。
