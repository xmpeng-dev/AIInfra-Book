1. 问题背景

ByteDance 常态化数千卡训数千亿参数 MoE。MoE 靠稀疏激活降训练成本,但系统视角下通信是瓶颈:实测通信占前向 43.6%、整训练 32%。两成因:① MoE 参数大 → 需更多 GPU 做模型并行 → 通信更多;② 稀疏计算在 fwd/bwd 各加 2 次 all-to-all(dispatch + combine)。硬件上算力增速远快于带宽 + 低精度进一步压缩计算 → 通信占比更突出(TP 扩多节点常 >50%)。

关键洞察: MoE 与 dense 的架构差异是层内的,也是通信开销主源。于是把每个 MoE 层约束在单节点内用 NVLink,避免跨节点 EP;节点间用 PP 分参数并 overlap 不同 micro-batch。

2. 三大支柱

支柱一:通信高效并行(降通信量)

  • Attention 用 SP(Ulysses 式)替 TP:TP 通信 2bsh(n-1)/n;SP 降到 2bsh(n-1)/n·(2+2/m)/n,NVLink domain=8 时约 TP 的 1/4。SP 复制权重但靠分层通信,参数同步开销与 TP 仅差 0.3–3.1%,额外显存仅 +1.2–5.4%。放弃 CP(causal mask 负载不均)。
  • FFN 用 EP 替 TP:TP 切 expert hidden 维伤 GEMM;EP 每卡完整 expert。自适应通信:top-k>n 时用 all-gather + 本地 scatter + reduce-scatter 替 A2A(ring 式、只与邻居通,更高效);自研 CUDA scatter/gather 算子替 torch。

支柱二:通信-计算 overlap

把 MoE 层 fwd/bwd 拆成独立 kernel(不走整块 autograd)。

  • Inter-op: holistic 调度在不同 stream 重排算子,把通信藏进无依赖计算;selective activation rematerialization 只存重算贵的激活,反向重算/重通信并 overlap 掉 → 激活内存 ↓~50% 不掉速。
  • Intra-op(关键路径通信): 通信切 tile 融进 compute kernel,device-memory barrier + tile 级通知去 host 干预。两类:attention 的 A2A+GEMM / GEMM+A2A(专用 copy engine + 全 SM 留给计算 + swizzle 对齐到达节奏 + 少量 SM 给通信);FFN 的 AG+scatter+GroupedGEMM / GroupedGEMM+gather+RS(按 expert 再按 source rank 排序,让每 tile 只依赖少数 rank)。

支柱三:通信压缩

  • DP: 梯度 FP32→BF16,但用 A2A 收分片 + FP32 归约(避免 BF16 ring 累加误差),梯度通信 ↓50%,精度损失可忽略。
  • FP8: TP 的 BF16 RS 换 FP8 A2A(E4M3) + FP32 归约;前向 per-token、反向 per-channel + group(128) 量化。

4. 与 monolith-moe / rocmoe 的对照(重点)

MegaScale-MoE 是我们 super-kernel 在「host/collective/op 级 overlap」维度上的最强生产级对照:证明 overlap 生产里稳拿 1.88×,并给了几把可直接搬的尺子。

MegaScale-MoE我们(monolith-moe / rocmoe)关系
intra-op:A2A+GEMM / GroupedGEMM+gather+RS 融进 kernel整前向 5 phase 融成 persistent super-kernel同类思想;他们半层一 kernel + device barrier
device-memory barrier + tile 级通知,去 host64-bit block_ready 位图 + receiver-pull收敛一致:tile/block 级就绪信号,无 host 介入
给通信分少量 SM + swizzle 对齐到达节奏comm_ratio 分 CU + XOR swizzle直接对应;「comm SM 数调到 comm≈comp」= comm_ratio 甜点
按 source rank 排序让 tile 只依赖少数 rankreceiver-pull:block 就绪即算同源,「等全部 token」→「等这个 tile 的 token」
通信压缩 FP32→BF16 / FP8 A2Abacklog:FP8/mxfp8 weights同类正交杠杆

三条最有用的结论

  • scale-up 判据可直接套 MI355X: R ≈ (3/2)·h_ffn·(bandwidth/peak),>1 才有 overlap 净收益。拿 XGMI 带宽 + MI355X BF16/FP8 peak + DSV3 h_ffn 代入,能先验判断给定 shape 下 overlap 上限——正是「512 t/g 赢、2048/8192 t/g 输」的一个理论解释器,值得算一遍写进 rocmoe README。
  • 「MoE 层锁节点内」是他们的前提,也正是我们的现状(单节点 8×MI355X/XGMI)。差异化:把 op 级 overlap 再推进到 in-kernel chunk 级 persistent kernel(他们仍是「半层一 kernel + copy engine」)。
  • 1.88× 是 op/collective 级 overlap 的生产上限参照: 我们要证明 in-kernel 融合能在 AMD/XGMI 上超过这个天花板,否则不如直接移植 MegaScale-MoE 式方案。这条写进价值主张。

5. 局限与复现

  • 依赖节点内 NVLink: 核心前提是「MoE 层锁节点内」,一旦 EP 跨出 NVLink 到 RDMA 级带宽,R>1 能否维持是公开问题(作者自述)。
  • holistic 调度靠手工(算子序 / 并发度 / 给通信几个 SM),自动化留 future work。
  • MoE 计算算子仍是 straggler 源(GroupedGEMM 资源控制致同步延迟、动态形状显存碎片、gating 小算子受 CPU jitter)。
  • 代码未开源(生产系统);Table 2 给全模型配置可复现思路。
