AutoOverlap:chunk 抽象 + 自动 kernel 内细粒度通信计算重叠编译器

arXiv 2026-01 UC San Diego + Meta Triton 源到源编译器

论文: arXiv:2601.20595
英文题名: AutoOverlap: Enabling Fine-Grained Overlap of Computation and Communication with Chunk-Based Scheduling
笔记路径: slab/papers/autooverlap/README.md
TL;DR 提出 communication chunk 抽象——把通信粒度从 kernel 结构和后端机制解耦,让 chunk 级 overlap plan 可从别的编译器移植/用户手写/模板实例化。基于 Triton 的源到源编译器 + runtime,自动把「本地 Triton kernel + chunk 调度」变成融合分布式 kernel,做三维自适应(通信后端 copy-engine/TMA/load-store · chunk 大小 · intra-chunk tile 顺序)+ autotuning。平均 1.3×、最高 4.7×。这批里唯一的编译器/自动化视角。

1. 问题

现有分布式编译器(Alpa/Mercury)只在 kernel/stream 级 overlap:每通信阶段一次 launch + kernel 边界 device-wide 同步 + wave quantization + 末尾无 overlap 的通信尾巴。手写细粒度(Flux/COMET/FlashOverlap/Triton-Distributed)虽好但每算子/架构/硬件都要专家手工,难泛化。

2. 核心方法

  • Chunk 抽象: 一个 chunk = 某通信操作关联的逻辑数据 + 产/消它的 tile;暴露 chunk 大小/后端/tile 顺序少数 knob。
  • 源到源 Triton 编译器 + runtime: 吃标注 kernel + chunk plan,重排 tile 跟随通信进度,无缝替换 PyTorch distributed 算子。
  • 三维自适应: ① 通信后端(copy engine ~400GB/s 但 host launch+连续;TMA 16 SM 300+GB/s 但限节点内;load-store 灵活可 in-network reduce 但吃 SM)按 chunk 选;② chunk 大小平衡吞吐 vs 同步;③ intra-chunk tile 顺序跟踪通信进度保局部性。

3. 主要实验

维度结果
端到端平均加速1.3×
最高4.7×
定位Chunk 粒度 + Compute/Comm/Schedule 全 Auto(vs Flux/COMET tile/chunk-manual)

4. 与 monolith-moe / rocmoe 的对照(重点)

唯一的编译器/自动化视角,对照我们「全手写 HIP super-kernel」的另一极。

AutoOverlap我们关系
chunk 抽象解耦通信粒度与 kernel 结构手写死 chunk/block 粒度⭐ 参数化成 chunk plan → 可 autotune/移植
通信后端按 chunk 自适应(copy engine/TMA/load-store)手写 HIP IPC 单一机制 + DTOLDS⭐ MI355X 上 XGMI DMA vs async-copy-to-LDS vs load/store 按 chunk 选
自适应 chunk 大小 + tile 调度固定 tile / kSubWGs与 UniEP autotuner 呼应
源到源编译器 + PyTorch distributed 无缝全手写 HIP C++⚠️ 手写换极致性能,AutoOverlap 自动化换泛化

结论

  • chunk 抽象给了把 super-kernel「参数化 + autotune」的框架思路:现在 chunk 粒度/搬运机制写死在 HIP,抽象成 chunk plan 就能自动搜最优而非人工返工。
  • 通信后端按 chunk 自适应在 AMD 尤值得试:MI355X 有 XGMI DMA / async direct-to-LDS / load-store 三条搬运路,当前基本只用一条,按 chunk 特性选后端可能是免费 overlap 增益。

5. 局限

  • 建在 Triton 源到源(表达力/性能边界内);评测多为常见算子级;TMA 后端限节点内点对点。
